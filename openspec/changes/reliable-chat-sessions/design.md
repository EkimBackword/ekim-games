# Design

## Context

`AuthStoreService` разделяет восстановление в пределах вкладки, самостоятельно запускает плановый refresh и поглощает ошибку logout. `AuthService` отзывает сессии при logout и в двух ветках обнаружения повторного refresh. `ChatGateway` хранит токен сокета и рассылает через весь namespace. `ChatStoreService` заменяет историю при подключении и обрезает список до 50. PostgreSQL хранит сообщения с индексом `(createdAt, id)`. Service Worker обслуживает оболочку и исключает API и Socket.IO из навигационного кэша.

## Goals / Non-Goals

**Цели**

- Задать границы согласованности refresh, отзыва и восстановления истории. Использовать существующие Angular-сервисы, общий слой Zod и PostgreSQL.

**Границы**

- Проект рассчитан на текущий запуск с одним процессом API. Распределённая координация шлюзов и сохранение состояния чата между перезагрузками страницы находятся за пределами change.

## Decisions

### Координация refresh и logout

Использовать эксклюзивный Web Lock общего origin для запросов, которые меняют общие cookies авторизации. Восстановление и плановый refresh каждой вкладки проходят через тот же lock. Читать CSRF cookie после получения lock и держать его до обработки HTTP-ответа браузером. Login, register и logout используют этот же lock при изменении cookies. Access JWT остаётся в памяти получившей его вкладки. Внутри вкладки переиспользовать выполняющийся refresh. При старте logout отменить таймер и инвалидировать результаты предыдущего восстановления по поколению локальной сессии, сохранив порядок сетевых операций.

Разделить успешный и ошибочный результаты logout в `AuthStoreService`. При обоих исходах очистить локальное состояние и уничтожить соединение чата. При ошибке перейти на публичный `/logout-error` с обычной ссылкой на `/`. Повторная навигация на главную может восстановить сессию, если сервер сохранил действующие cookies. Альтернатива с выдачей нового токена для повторно использованного refresh JWT меняет согласованное правило отзыва.

### Граница отзыва и авторизация сокета

Возвращать проверенные `sid` и `exp` из серверной проверки токена. Регистрировать только авторизованные сокеты в реестре по `sid`. Добавить проверяемое событие обновления авторизации с подтверждением и переназначением таймера истечения. Задержанные обновления и таймеры сверять с текущим поколением авторизации сокета. При смене access JWT обновлять также данные следующего handshake. После серверного отключения повторное подключение инициируется клиентом только при наличии действующей локальной сессии.

Вынести завершение отзыва для logout и обеих веток повторного refresh в общий путь. Сериализовать допуск и обновление сокета с отзывом того же `sid`. После успешной записи отзыва синхронно убрать все его сокеты из реестра и закрыть их до завершения операции. REST и Socket.IO публикуют через один путь, который проверяет членство и срок непосредственно перед каждым `emit`, без асинхронного промежутка между проверкой и постановкой в отправку. При асинхронной обработке использовать актуальную запись реестра, включая проверку после ожидания. Пакеты, поставленные в отправку до завершения отзыва, могут находиться в транспорте. Проверка только при входящих событиях оставляет неактивные сокеты в рассылке.

### Курсоры истории и восстановления

Для ранних страниц использовать существующий порядок `(createdAt, id)` и эксклюзивный курсор. Сохранить массив в ответе `GET /api/chat/messages`, добавить параметр `before` и метаданные следующей страницы и позиции восстановления в заголовках. Начальный массив и позицию восстановления получать из одного согласованного снимка базы.

Для восстановления использовать отдельную возрастающую позицию записи и постраничный REST-запрос после позиции с фиксированной верхней границей. Назначать позиции всем записям REST и Socket.IO через строку счётчика в той же транзакции, что и вставка. Блокировка строки до commit обеспечивает порядок видимости. Независимое значение sequence, выданное до commit, может стать видимым позже уже пройденной позиции. Курсоры передавать как строки и валидировать общими схемами.

Подписать слушатель Socket.IO до установления соединения. После начального снимка и каждого переподключения дочитать страницы до верхней границы. Продвигать позицию только по успешно применённым страницам REST. События и страницы объединять по `id` в порядке `(createdAt, id)`. Прерывание восстанавливается с последней подтверждённой позиции. Запоздалые ответы предыдущего соединения отбрасываются по поколению. Состояние загруженных страниц, исходящих сообщений и черновика принадлежит открытой странице, а готовность отправки зависит от завершения восстановления.

### Подтверждение исходящих сообщений

Клиент генерирует UUID `clientMessageId` один раз на исходящее сообщение. Хранить его в nullable-поле с уникальностью пары `(userId, clientMessageId)`. Сохранение и выделение позиции выполняются атомарно. При конфликте идентификатора вернуть существующую запись для того же нормализованного текста и отклонить другой текст. Рассылку инициирует только создавшая запись операция. Существующие записи и REST-отправки используют `null`.

Различать положительный ACK, явный отказ и неопределённый результат. После тайм-аута при доступном чате или при восстановлении сверять ожидающие идентификаторы авторизованным REST-запросом с ограниченным размером пачки и фильтром по текущему автору. Ответ возвращает сохранённые записи и позволяет отличить подтверждённое отсутствие от ошибки запроса. Объединять ACK, историю и события по серверному `id`, а исходящую запись связывать с ним по идентификатору попытки. В авторскую копию события добавлять `clientMessageId`, чтобы событие, пришедшее до ACK, сразу заменяло временное представление. Остальным получателям отправлять публичную форму сообщения. Сопоставление по тексту неоднозначно при одинаковых сообщениях. Тайм-аут ACK не является отказом сервера.

Использовать нативную кнопку с текстовым оформлением Taiga UI, фокусируемые статусы с текстовыми подсказками и объявление изменения статуса для скринридера. Включить нужные ресурсы иконок по существующему способу доставки Taiga UI.

## Risks / Trade-offs

- Web Locks требует поддерживаемого контекста браузера → проверить матрицу браузеров проекта и HTTPS или локальную разработку. При отсутствии механизма показать явную ошибку восстановления и исключить параллельную ротацию без координации.
- Разрыв во время ответа refresh может оставить браузер со старой cookie → сохранить серверное правило отзыва и существующий повторный вход для потерянной сессии.
- Единый счётчик сериализует короткие транзакции записи → держать внутри только проверку идемпотентности и запись. Рассылать после commit.
- Сервер может завершить запись после проверки отсутствия → позднее подтверждение объединяется с записью, а ручной повтор с тем же идентификатором безопасен.
- Socket.IO-контракт меняется одновременно на клиенте и сервере → при развёртывании обновить открытые вкладки со старой версией приложения.

## Migration Plan

1. Приостановить запись сообщений на время миграции. Добавить nullable-идентификатор попытки, позиции восстановления и счётчик. Заполнить позиции существующих сообщений в порядке `(createdAt, id)`, установить счётчик по максимальной позиции и создать ограничения и индексы.
2. Развернуть API и web с общими контрактами, проверить старые сообщения, вход из двух вкладок и восстановление чата. Исключить новые API чтения из кэширования.
3. При откате развёртывать API и web согласованно. Перед возобновлением записей старым API обеспечить совместимую схему или выполнить обратную миграцию с сохранением строк сообщений. При повторном развёртывании сверить полноту и порядок позиций.
