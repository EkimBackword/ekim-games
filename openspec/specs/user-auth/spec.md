# user-auth Specification

## Purpose

Пользователи создают учётную запись по никнейму, входят в приложение и восстанавливают сессию при повторном открытии сайта.

## Requirements

### Requirement: Регистрация по никнейму

Система SHALL принимать через `POST /api/auth/register` никнейм из 3–24 букв, цифр и символов `_`, `.`, `-` и пароль длиной 12–128 символов. Никнейм SHALL быть уникальным после нормализации Unicode NFKC и приведения к нижнему регистру. Пароль SHALL храниться в виде хэша.

#### Scenario: Регистрация с допустимыми данными

- **WHEN** гость отправляет допустимые данные с новым никнеймом
- **THEN** система создаёт учётную запись и сессию
- **AND** веб-клиент после успешной регистрации открывает `/`

#### Scenario: Совпадение никнейма

- **WHEN** нормализованный никнейм совпадает с уже зарегистрированным
- **THEN** API возвращает `409 Conflict`

#### Scenario: Недопустимые данные

- **WHEN** данные запроса не соответствуют контракту регистрации
- **THEN** API возвращает `400 Bad Request`

### Requirement: Вход с паролем

Система SHALL принимать никнейм и пароль через `POST /api/auth/login` и выдавать сессию при совпадении учётных данных. При поиске пользователя SHALL применяться те же правила нормализации никнейма, что и при регистрации.

#### Scenario: Вход с верными данными

- **WHEN** гость вводит верный пароль для существующего никнейма
- **THEN** API выдаёт сессию и веб-клиент открывает `/`

#### Scenario: Ошибка входа

- **WHEN** в корректно сформированном запросе указан неизвестный никнейм или неверный пароль
- **THEN** API возвращает `401 Unauthorized` с одинаковым сообщением для обеих причин

### Requirement: Выдача и обновление сессии

При регистрации, входе и успешном `POST /api/auth/refresh` API SHALL возвращать `accessToken` и `user` с полями `id` и `nickname`. Access JWT действует 10 минут и хранится в памяти веб-клиента. Refresh JWT действует 7 дней с момента выдачи и передаётся в HttpOnly cookie с `SameSite=Strict`. Каждый успешный refresh SHALL заменять refresh JWT. Вкладки одного origin в одном профиле браузера SHALL согласовывать восстановление и плановое обновление общей сессии.

#### Scenario: Восстановление после перезагрузки

- **WHEN** пользователь перезагружает страницу с действующими refresh и CSRF cookies
- **THEN** веб-клиент восстанавливает сессию через `POST /api/auth/refresh` и получает новый access JWT

#### Scenario: Одновременный refresh в нескольких вкладках

- **WHEN** две или более вкладки одновременно восстанавливают или обновляют одну активную сессию
- **THEN** один refresh JWT не отправляется параллельно несколькими вкладками
- **AND** каждая вкладка получает действительный access JWT, сессия остаётся активной

#### Scenario: Повторное использование токена

- **WHEN** API получает ранее использованный refresh JWT с действующей подписью и сроком действия для активной сессии при валидной проверке CSRF
- **THEN** API отклоняет запрос и отзывает сессию

### Requirement: Выход и проверка CSRF

API SHALL проверять совпадение cookie `eg_csrf` и заголовка `x-csrf-token` для refresh и logout. При успешном `POST /api/auth/logout` API SHALL очистить cookies сессии и отозвать сессию, если запрос содержит действительный refresh JWT. При любом результате logout веб-клиент SHALL очистить локальную авторизацию в инициирующей вкладке и закрыть её чат.

#### Scenario: Выход из приложения

- **WHEN** авторизованный пользователь выходит через веб-интерфейс и API успешно обрабатывает запрос
- **THEN** веб-клиент очищает локальную сессию и открывает `/login`
- **AND** access JWT отозванной сессии отклоняется при следующей проверке

#### Scenario: Серверный выход не подтверждён

- **WHEN** запрос logout завершается ошибкой HTTP, сети или тайм-аутом
- **THEN** веб-клиент очищает локальную авторизацию, закрывает чат и открывает `/logout-error`
- **AND** страница доступна без активной локальной сессии и показывает сообщение «Не удалось подтвердить выход на сервере» и ссылку на `/`
- **AND** переход по ссылке применяет обычные правила главного маршрута, включая восстановление сессии при действующих cookies

#### Scenario: Отсутствие или несовпадение CSRF

- **WHEN** в запросе refresh или logout отсутствует cookie или заголовок CSRF либо их значения различаются
- **THEN** API возвращает `403 Forbidden`

### Requirement: Доступ к страницам

Веб-клиент SHALL определить состояние сессии перед выбором маршрута и предоставлять главную страницу `/` авторизованному пользователю, а `/login` и `/register` гостю.

#### Scenario: Гость открывает главную

- **WHEN** пользователь открывает `/` и восстановить сессию не удаётся
- **THEN** веб-клиент открывает `/login`

#### Scenario: Авторизованный пользователь открывает страницу входа

- **WHEN** пользователь с активной сессией открывает `/login` или `/register`
- **THEN** веб-клиент перенаправляет его на `/`

#### Scenario: Неизвестный адрес

- **WHEN** пользователь открывает неизвестный маршрут
- **THEN** веб-клиент применяет правила маршрута `/`

### Requirement: Адаптивная оболочка страниц авторизации

Веб-клиент SHALL отображать страницы входа и регистрации в общей композиции с логотипом Ekim Games, фоном деревянной столешницы и формой на пергаменте. Декор SHALL оставлять текст читаемым и элементы формы доступными.

#### Scenario: Широкий экран

- **WHEN** гость открывает любую страницу авторизации на широком экране
- **THEN** он видит логотип, приветствие слева, форму справа и игровые предметы вокруг свободной области текста и формы

#### Scenario: Узкий экран

- **WHEN** гость открывает любую страницу авторизации на узком экране
- **THEN** он видит логотип и пергаментную форму на деревянном фоне
- **AND** приветствие и разбросанный по столу декор скрыты
- **AND** поля, сообщения об ошибках и кнопка доступны без горизонтальной прокрутки

#### Scenario: Заполненные поля при тёмной настройке браузера

- **WHEN** гость открывает вход или регистрацию при тёмной настройке браузера или системы и заполняет поля вручную либо автозаполнением
- **THEN** форма и поля сохраняют светлое оформление, а подписи и введённые значения остаются читаемыми

### Requirement: Переключение между входом и регистрацией

Веб-клиент SHALL показывать в пергаментной панели ссылки «Вход» и «Регистрация», доступные с клавиатуры. Текущий режим SHALL определяться маршрутом, выделяться визуально и обозначаться для вспомогательных технологий.

#### Scenario: Переключение формы

- **GIVEN** гость открыл `/login`
- **WHEN** он активирует «Регистрация»
- **THEN** веб-клиент открывает `/register`, показывает форму регистрации и отмечает текущую ссылку
- **AND** ссылка «Вход» ведёт обратно на `/login`

#### Scenario: Прямой переход и история браузера

- **WHEN** гость открывает `/register` по прямой ссылке или возвращается на `/login` через историю браузера
- **THEN** форма и выделение ссылки соответствуют открытому адресу

### Requirement: Поля и состояния форм авторизации

Веб-клиент SHALL показывать никнейм и пароль на обеих страницах и подтверждение пароля при регистрации. Парольные поля SHALL по умолчанию скрывать введённые символы и позволять переключать видимость. Формы SHALL сохранять текущие проверки, сообщения об ошибках и блокировку повторной отправки во время запроса.

#### Scenario: Ошибка регистрации

- **WHEN** гость пытается зарегистрироваться с несовпадающими паролями
- **THEN** форма показывает ошибку подтверждения и не отправляет данные на сервер

#### Scenario: Ошибка входа

- **WHEN** сервер отклоняет учётные данные
- **THEN** форма показывает сообщение об ошибке и позволяет повторить попытку
