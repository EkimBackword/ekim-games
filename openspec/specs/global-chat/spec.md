# global-chat Specification

## Purpose

Общий чат позволяет авторизованным пользователям читать недавние сообщения и общаться в реальном времени с главной страницы.

## Requirements

### Requirement: Доступ к чату по активной сессии

API SHALL требовать Bearer access JWT для REST-запросов чата и `auth.accessToken` в handshake Socket.IO для namespace `/chat`. Сервер SHALL проверять действительность токена и активность сессии при REST-запросе, подключении Socket.IO и каждой отправке через Socket.IO. Сервер SHALL допускать сокет к рассылке только после авторизации и связывать его с `sid` из проверенного токена.

#### Scenario: Запрос без активной сессии

- **WHEN** клиент запрашивает историю или отправляет сообщение по REST с недействительным токеном либо отозванной сессией
- **THEN** API возвращает `401 Unauthorized`

#### Scenario: Отправка после отзыва сессии

- **WHEN** уже подключённый клиент отправляет сообщение после отзыва его сессии
- **THEN** сервер отключает сокет без сохранения сообщения

#### Scenario: Незавершённая авторизация сокета

- **WHEN** handshake ещё проверяется либо отклонён
- **THEN** сокет не получает сообщения чата

### Requirement: История общего чата

`GET /api/chat/messages` SHALL возвращать не более 50 последних сохранённых сообщений в порядке от старых к новым. Каждое сообщение SHALL содержать `id`, `authorNickname`, `text` и `createdAt` в формате ISO. API SHALL позволять запрашивать предыдущую страницу по курсору и сообщать, есть ли более ранние сообщения.

#### Scenario: История содержит более 50 сообщений

- **WHEN** авторизованный клиент запрашивает историю, а в БД есть больше 50 сообщений
- **THEN** API возвращает 50 последних сообщений по возрастанию времени создания
- **AND** для сообщений с одинаковым временем создания порядок определяется по `id`

#### Scenario: Запрос предыдущей страницы

- **WHEN** клиент запрашивает страницу по курсору самого раннего сообщения загруженной страницы
- **THEN** API возвращает до 50 более ранних сообщений по тому же порядку без повторения сообщения на границе
- **AND** появление новых сообщений не сдвигает эту границу

### Requirement: Отправка и рассылка сообщений

Система SHALL принимать `{ text }` через `POST /api/chat/messages` и `{ text, clientMessageId }` через событие `chat:send-message`. После удаления пробелов по краям текст MUST содержать от 1 до 2000 символов. Сервер SHALL сохранить сообщение от имени текущего пользователя перед рассылкой `chat:message-created` и положительным подтверждением Socket.IO.

#### Scenario: Отправка через интерфейс чата

- **WHEN** пользователь отправляет допустимый текст через интерфейс при подключённом сокете
- **THEN** клиент отправляет `chat:send-message`, а сервер сохраняет сообщение и рассылает его в `chat:message-created`
- **AND** сервер подтверждает сохранение, возвращая запись и идентификатор попытки отправителю
- **AND** веб-клиент отображает одну запись независимо от порядка получения подтверждения и рассылки

#### Scenario: Отправка через REST

- **WHEN** авторизованный клиент отправляет допустимый текст через REST
- **THEN** API возвращает сохранённое сообщение и сервер рассылает его в `chat:message-created`

#### Scenario: Недопустимый текст

- **WHEN** клиент отправляет пустой после удаления пробелов или слишком длинный текст
- **THEN** сервер отклоняет сообщение без сохранения и рассылки
- **AND** REST отвечает `400 Bad Request`, а Socket.IO отправляет автору `chat:error` и возвращает отрицательное подтверждение

### Requirement: Отображение сообщений на главной

Веб-клиент SHALL загружать последние 50 сообщений через REST при открытии чата, подгружать предыдущие страницы по запросу и объединять историю с сообщениями из Socket.IO по уникальному `id`. При восстановлении чата на открытой странице веб-клиент SHALL сохранять загруженные страницы и черновик.

#### Scenario: Получение нового сообщения

- **WHEN** подключённый клиент получает `chat:message-created` с корректными данными
- **THEN** веб-клиент добавляет сообщение, если его `id` ещё отсутствует в списке
- **AND** ранее загруженные сообщения остаются в списке

#### Scenario: Пользователь загружает более раннюю историю

- **WHEN** доступна предыдущая страница и пользователь запрашивает её
- **THEN** веб-клиент добавляет полученные сообщения к уже показанным без дублей
- **AND** после последней страницы действие подгрузки больше недоступно

#### Scenario: Попытка отправки без соединения

- **WHEN** соединение с чатом недоступно или ещё восстанавливается
- **THEN** кнопка отправки заблокирована, отправка через форму не запускается и текст остаётся в поле ввода

### Requirement: Обновление и завершение авторизации сокета

Сервер SHALL обновлять авторизацию открытого сокета только по действующему access JWT той же активной сессии. При истечении текущего токена сервер SHALL исключать сокет из рассылки и закрывать его. При отзыве сессии сервер SHALL исключать из рассылки и закрывать все её сокеты. После завершения отзыва сервер SHALL исключать постановку новых сообщений в отправку любому сокету этого `sid`.

#### Scenario: Смена токена без переподключения

- **WHEN** открытый авторизованный сокет получает подтверждение обновления по новому токену с тем же `sid` до истечения текущего
- **THEN** соединение остаётся открытым, а срок его авторизации определяется новым токеном

#### Scenario: Токен другой сессии

- **WHEN** клиент запрашивает обновление авторизации по токену другого `sid`
- **THEN** сервер отклоняет обновление и не переносит сокет в другую сессию

#### Scenario: Истечение токена у неактивного сокета

- **WHEN** срок текущего токена истекает без принятого обновления
- **THEN** сервер исключает сокет из рассылки и закрывает его даже без входящих событий от клиента

#### Scenario: Отзыв сессии при конкурентной рассылке

- **WHEN** logout или обнаружение повторного использования refresh JWT отзывает сессию с несколькими сокетами
- **THEN** все её сокеты исключены из рассылки и закрыты к завершению отзыва
- **AND** даже рассылка, начатая до отзыва, не ставит новые сообщения в отправку этому `sid` после завершения отзыва
- **AND** сокеты другой активной сессии продолжают получать сообщения

### Requirement: Восстановление пропущенных сообщений

Веб-клиент SHALL после первого подключения и каждого переподключения сверять историю с сервером от последней подтверждённой позиции и загружать все пропущенные сообщения. Клиент SHALL объединять догрузку и поток событий по `id` и считать восстановление завершённым после успешного получения всех страниц до контрольной границы.

#### Scenario: Разрыв дольше одной страницы

- **WHEN** во время разрыва сохранено больше 50 сообщений и во время восстановления приходят новые события
- **THEN** веб-клиент догружает все пропуски без дублей, сохраняя старые страницы и черновик
- **AND** после восстановления продолжает отображать новые события

#### Scenario: Сообщение на границе первого подключения

- **WHEN** сообщение сохранено между загрузкой начальной истории и подпиской на события
- **THEN** оно появляется при сверке после подключения

#### Scenario: Повторный разрыв при догрузке

- **WHEN** соединение прерывается до завершения сверки
- **THEN** после следующего подключения клиент продолжает восстановление с подтверждённой позиции без потери сообщений

### Requirement: Повтор одной попытки отправки

Сервер SHALL хранить связь сохранённого сообщения с `clientMessageId` в пределах автора и позволять автору проверить сохранение по этому идентификатору. Повтор той же попытки с тем же нормализованным текстом SHALL подтверждать ту же запись без повторной рассылки. Повтор идентификатора с другим текстом SHALL отклоняться.

#### Scenario: Конкурентные повторы и потерянное подтверждение

- **WHEN** сервер принимает несколько допустимых запросов одной попытки
- **THEN** в базе остаётся одна запись, успешные ответы указывают на неё, а рассылка происходит один раз

#### Scenario: Подмена текста при повторе

- **WHEN** автор повторяет использованный идентификатор с другим нормализованным текстом
- **THEN** сервер отклоняет запрос без изменения сохранённой записи

### Requirement: Статусы и ручной повтор отправки

Веб-клиент SHALL показывать «Отправляется» с иконкой Taiga UI `clock`, «Отправлено» с `check` и ошибку с красной `triangle-alert`. Статусы SHALL иметь подсказки при наведении и фокусе и текст для скринридера. После ошибки SHALL быть доступна кнопка «Отправить повторно» с оформлением текста, которая использует исходный идентификатор и текст.

#### Scenario: Подтверждение не пришло

- **WHEN** сообщение отправлено, но результат неизвестен из-за разрыва или тайм-аута
- **THEN** исходящее сообщение остаётся в списке со статусом «Отправляется»
- **AND** после восстановления связи или при доступном соединении после тайм-аута клиент сверяет попытку с сервером

#### Scenario: Сверка исходящего сообщения

- **WHEN** сервер успешно отвечает на сверку попытки
- **THEN** найденное сообщение отображается как «Отправлено», а при подтверждённом отсутствии клиент показывает ошибку и кнопку «Отправить повторно»
- **AND** сбой самой сверки оставляет статус «Отправляется»

#### Scenario: Отказ и повтор отправки

- **WHEN** сервер явно отклоняет отправку либо сверка подтверждает отсутствие записи
- **THEN** веб-клиент показывает ошибку
- **AND** при активном соединении кнопка повторно отправляет ту же попытку и возвращает статус «Отправляется»
- **AND** клиент не повторяет отправку автоматически

#### Scenario: Доступность статуса

- **WHEN** пользователь наводит указатель на статус или переводит на него фокус с клавиатуры
- **THEN** отображается текстовая подсказка, статус доступен скринридеру, а кнопку повтора можно активировать с клавиатуры
